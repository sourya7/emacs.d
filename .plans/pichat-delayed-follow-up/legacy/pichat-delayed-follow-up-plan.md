# PiChat: manually scheduled continuation (implementation plan)

## Scope and recommendation

Add an opt-in **Emacs-owned, one-shot** schedule to the exact owning PiChat chat for either (a) `continue` or (b) **compact successfully, then `continue`**. Accept a relative duration such as `5h` (possibly a clock time as a later enhancement), show the absolute due time, and provide list/status and cancel controls. No automatic Codex-limit detection, quota query, account switching, third-party extension dependency, background daemon, or silent restart recovery in v1. A five-hour delay is **five hours from scheduling**, not a promise that Codex's rolling 5-hour window has reopened.

Prefer PiChat's existing RPC and Emacs timers over a Pi extension for a *manual* timer: the user supplies the time, so no provider credentials or Pi-side usage API are needed. Do **not** issue `follow_up` when creating the schedule: Pi delivers that queue as soon as the current agent finishes. At the due time issue a normal `prompt` (`continue`) only after validation. For compact-and-continue, send `compact` first and issue `prompt` only from its verified successful completion path. This preserves PiChat ownership and avoids creating work in the wrong Pi session.

## Evidence reviewed (installed Pi 1.4.0; no code changed)

- `pichat/GLOSSARY.md`: a **runtime** is the managed RPC process and Emacs session object; the **Pi session** is the conversation ID; a **saved session file** is not either one. A **follow-up message** is Pi's queue for after the current run, not a clock-based job. Source rebinding and process generation are distinct safety boundaries. This plan uses those terms.
- `pichat/README.md`, `pichat/pichat-chat.el` (`pichat-chat-follow-up`, `pichat-chat-compact`): PiChat exposes an immediate Pi follow-up queue and manual compact RPC, but no delayed user-facing job. Chat status already supports keyed lines via `pichat-chat--set-status`.
- Pi 1.4.0 `docs/rpc-commands.md`: `follow_up` delivers when the agent finishes; `prompt` without streaming behavior is rejected while streaming; `prompt` acceptance is distinct from agent completion. `compact` returns a result on success and fails on unsuccessful compaction. `get_state` reports `isStreaming`, `isCompacting`, `pendingMessageCount`, `sessionId`, and `sessionFile`; `get_entries` returns `leafId` and accepts a cursor.
- Pi 1.4.0 `docs/rpc.md`, `docs/json.md`: `agent_end` is **not** a final idle boundary because retries/queued work may follow; `agent_settled` is. The client must not assume `prompt` success means the task finished.
- `pichat/pichat-rpc.el`: `pichat-rpc-prompt`, `pichat-rpc-compact`, `pichat-rpc-get-state`, `pichat-rpc-get-entries` and correlated success/error callbacks already exist. RPC response dispatch is process-generation guarded; a failed command without an error callback merely emits a diagnostic, so the scheduler must supply one. Successful rebind commands emit `session-rebinding` before downstream callbacks.
- `pichat/pichat-chat.el`: `pichat-chat-owned-buffer(session, t)` validates current ownership/source, `pichat-chat--source-token` records chat source generation/ID/file, `pichat-chat--reset-for-source` invalidates source-derived work, `pichat-chat--on-session-ended` and kill-buffer hooks clean up chat work. A verified same-source reconfiguration may keep the same source while replacing the **process**, so capture process generation separately. The chat's canonical entry cache and `pichat-entry-cache-leaf-id` in `pichat/pichat-pi.el` provide a local branch snapshot.
- `pichat/test/pichat-test-integration.el`: the real-Pi fake-provider suite already demonstrates successful `compact` returning before the next prompted model response, and failed `compact` returning via an error callback plus `compaction_end.errorMessage`; the fake provider supports scripted model calls. `pichat/TESTING_GUIDELINES.md` requires isolated Pi config and real-Pi tests for RPC-crossing behavior.
- Installed `pi --version` reports 1.4.0. `pichat/PI_COMPATIBILITY.md` records a passing full suite on 1.4.0, while its formal review/verification watermarks remain 1.3.0; do not silently advance those watermarks for this feature.

## Behavior contract to implement

1. **Arm:** interactive `pichat-chat-schedule` chooses `continue` or `compact-then-continue`, reads and validates a positive bounded duration and a nonempty continuation prompt (default `continue`), previews the resulting absolute local due time, and creates at most **one pending job per chat**. Offer an explicit replace confirmation if one exists. Start only for a live, idle Pi-backed runtime with a bound, synchronized source, no active restart/rebind, and an empty Pi queue. For v1, require the chat's canonical entry cache to be current and capture its active `leafId` (including `nil` for an empty session). Do not consume or change the user's unsent draft/attachments.
2. **Ownership:** capture the exact chat buffer, session object/runtime ID, Pi session ID, source generation and source path, process object and process generation, branch leaf, model provider/ID, due timestamp, and a unique job token. Identity alone is insufficient: a new run in the same Pi session must invalidate the scheduled intent. V1 cancels a job on source rebinding, model change, runtime stop/restart, chat-buffer death, explicit cancel, **or intervening user/agent work** that changes the active branch. No job follows a saved file into a new runtime. No persistence: quitting Emacs loses the job; stopping Pi cancels it. Explain this in the command/UI.
3. **At deadline:** Emacs one-shot `run-at-time`, with an absolute stored due timestamp, wakes when the Emacs event loop is able to run (not necessarily at an exact wall-clock second). Clear/disarm the timer before side effects; only the current job token may act. If too early due to a clock change, re-arm for the remaining duration. Check buffer, Pi backend, exact live process/generation, source identity/token and restart state; then asynchronously request `get_state` and a cheap `get_entries`/leaf check. Confirm idle (`isStreaming`/`isCompacting` false, no pending messages) and matching session ID/file and leaf. If these checks fail, **cancel with a visible reason** rather than quietly queueing into unrelated work or polling indefinitely. No automatic retry of an ambiguously accepted RPC submission.
4. **Continue action:** submit via `pichat-backend-submit-prompt` with no streaming behavior; install both success and error callbacks. A successful RPC response must have disposition `started` (not `queued` or `handled`); otherwise report that no guaranteed continuation ran. If rejected or timed out, report an explicit, manually recoverable failure; do not send the same prompt again automatically. Do not insert text into or clear the user's current draft.
5. **Compact-then-continue action:** revalidate immediately before `pichat-rpc-compact`. Treat only the correlated successful `compact` response with a usable result as successful; do not infer success from `compaction_end` alone (aborted or failed events exist). On failure, cancellation, transport loss, or ambiguous timeout **do not** continue. On success, perform another same-source/process and idle check before submission; the branch leaf is expected to have changed due to compaction, so verify it represents the expected compaction on the active branch, and reject intervening user/agent work. Submit exactly one fresh prompt through the normal prompt path. Avoid an unconditional `follow_up` queued before compaction. Compaction consumes provider quota, so it may fail if the user-supplied delay ended before capacity returned.
6. **Visibility and controls:** a dedicated compact chat status entry displays action, prompt summary, and due time; show a distinct phase for validating/compacting/submitting, and retain a bounded failure notice until acknowledged or replaced. Provide `pichat-chat-cancel-schedule`; cancellation during compact must prevent the *next* prompt but must not claim to abort a compact RPC already in flight. No secrets or provider error body in status text. One-job policy keeps cancellation and diagnostics unambiguous.

## Design details / ordering to verify during implementation

- Put the coordinator and pure duration/time parsing in a small `pichat/pichat-chat-schedule.el` module (no `require` of `pichat-chat.el`). Let `pichat-chat.el` supply chat status, exact ownership/identity, and event hooks, or pass these as callbacks; keep protocol requests in the existing `pichat-rpc.el`/backend layer. Avoid reusing `pichat-chat-send-input`: that function owns and clears the interactive editor and its attachments.
- Subscribe to `session-rebinding`, `session-ended`, `agent-start`, and appropriate response/message lifecycle events for cancellation. Avoid cancelling on the scheduler's own prompt or the expected compaction; use a phase/token guard. Check what a manual or extension-triggered model switch emits in RPC: if no reliable model-change event reaches PiChat, compare fresh `get_state.model` at due time (and before the final prompt) instead of trusting a cached field. Never use `agent_end` as a final-idle test.
- Decide whether a cheap `get_entries` call with `since=leafId` works for `nil`/empty caches; if not, request entries without a cursor. A `leafId` comparison alone could miss a switch away and back to the same leaf, hence the source-generation and process-generation checks and event cancellation. A post-compaction leaf change is expected; test that the new active leaf corresponds to a successful compaction rather than skipping this check.
- Preserve an explicit state machine: `scheduled -> validating -> compacting (optional) -> validating -> submitting -> accepted/failed/cancelled`, with idempotent cancellation, one-shot timer cleanup, and stale callback suppression. Do not cancel Pi's shared `compact` RPC request simply to hide a late response; invalidated callbacks must become no-ops. Guard exceptions in timer callbacks and all rejection/timeout paths so the UI never claims that `continue` ran when it did not.
- Process generation is required even for same-source in-place reconfiguration. If a chat is killed while `pichat-chat-stop-session-on-kill` is nil, its job still cancels; it must not send through a retained runtime with no owning chat.

## Verification and release gates

- Emacs-only ERT: duration bounds/invalid input; exact due time; replacement and cancellation; draft/images untouched; timer fires once despite reentry; stale job token; early clock change; source switch (including away-and-back), model change, process replacement and kill; busy/queued state; changed branch leaf; RPC accept/reject/timeout/handled; compaction success/failure/abort/timeout and late callbacks; cancellation while compacting; no duplicate prompt.
- Isolated real-Pi RPC fake-provider tests: scheduled `continue` is **not** delivered before a controllable timer fires; after fire exactly one scripted model call consumes `continue`; compact-and-continue uses a deterministic compaction summary call followed by the continuation call **in that order**; provider compaction error yields no continuation; session switch or independent user prompt before deadline yields no delayed work. Reuse the test harness and fixtures without accessing real account credentials. Observe both the prompt's correlated disposition and the eventual `agent_settled`/script-consumed assertion.
- Run `pichat/test/run-tests.sh` then `pichat/test/run-tests.sh --full`; report failures. Update `pichat/README.md` with exact command/UI behavior and Emacs lifetime limits, and keep terminology aligned with `pichat/GLOSSARY.md`. Do not update `PI_COMPATIBILITY.md` watermarks without its separate documented upstream-review workflow.

## Explicit non-goals / follow-ups

- No automatic Codex 5-hour reset calculation: Pi RPC does not return a reliable quota reset timestamp; that needs a separately designed Pi-side provider-auth/usage bridge or a vetted extension such as `pi-auto-wait`.
- No durable scheduling across Emacs exit, Pi process exit, or SSH host loss. A later version could persist jobs in PiChat-managed Emacs storage and require explicit user confirmation and session revalidation on restore; do not silently restart work in a saved session file.
- No guarantee of exactly-once provider execution when a submitted `prompt` response is lost: fail closed, show an ambiguous state, and require the user to inspect the active Pi session before retrying.
