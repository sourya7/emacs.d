* Goal
Add lightweight native PiChat jobs with reusable instructions, inspectable runs,
optional scheduling, and optional plan-phase targeting. Preserve room for simple
conditional chaining without building a general workflow engine. Design the UI
first and obtain explicit user acceptance before feature implementation.

* Scope
- Jobs DO NOT require plans. Ordinary prompt jobs and optional plan-backed jobs
  share execution, scheduling, history, and inspection machinery.
- Included: accepted UI example; manual/background execution; durable definitions
  and run records; optional exact-plan-phase adapter; one-shot and fixed-interval
  scheduling; tests and documentation. Conditional chaining is a later scope
  requiring separate execution authorization.
- No blanket single-run-per-project restriction. Limit overlapping occurrences
  of a job, total concurrency, and conflicts over shared mutable resources.
- Excluded initially: external workflow engines or new async-library dependencies,
  execution while Emacs is closed, distributed workers, automatic retries or
  interrupted-work replay, implicit approvals, arbitrary Lisp jobs, cron/calendar
  recurrence, graph editors, fan-in joins, dynamic graphs, complex branching DSLs,
  automatic worktree provisioning, sandbox guarantees, durable workflow resumption,
  and exactly-once dispatch guarantees across crashes.
- Also deferred: stable phase IDs/Org ID insertion and automatic plan-modification
  detection, diffing, or reauthorization based on content changes.
- User explicitly accepted the revised UI and authorized proceeding on 2026-10-31.
  Phase 2 was the selected execution scope; later phases do not start automatically.
- Follow-up planning revision: result-first reports, full-response capture, offline
  transcript inspection, explicit conversational continuation and finished-runtime
  cleanup belong to Phase 2. Evaluate an optional ask-user extension separately;
  adoption/custom implementation is not yet selected. This request authorizes
  plan revision/research only, not implementation. Subsequently the user explicitly
  requested running Phase 2; revised implementation and isolated evaluation are
  now authorized, but extension adoption remains a separate decision.

* Acceptance criteria
- Phase 1 presents a concrete example for job creation, manual execution,
  scheduling, listing, run history/results, required input, failures, and trigger
  provenance. Cover ordinary jobs and one-shot plan-phase work, including a phase
  that stops for human acceptance. The user explicitly accepts the example;
  approval of the plan or silence is not UI acceptance.
- Ordinary jobs work without plan.org. One-off submissions need not be saved as
  named definitions; they produce ordinary runs with captured definition data.
- Runs use fresh independent runtimes/Pi sessions without changing the preferred
  interactive runtime, current-runtime selection, or focus. Inspection never
  implicitly executes work. Users can cancel and inspect exact owning chats.
- Submission acceptance, agent settlement, result synchronization, and domain
  completion remain distinct. Agent completion alone cannot complete a phase,
  satisfy human acceptance, or dispatch its successor.
- Definitions and run metadata survive restart. Ambiguous/interrupted runs are
  explicitly inspectable and never automatically retried, resumed, or declared
  successful. Saved Pi sessions retain conversation evidence independently.
- One active occurrence per definition and a configurable global limit apply.
  Compatible work can run concurrently in one project; conflicting modifiers
  sharing a workspace or authoritative plan are serialized by default.
- Explicitly selected plan phases have bounded authorization, eligibility checks,
  and stop boundaries. Completed/paused/cancelled/archived, unresolved-gate,
  missing/ambiguous phase, or uncertain-execution cases cannot silently run.
  Phase selection uses plan path and heading path, not a stable ID. Runs use the
  current saved plan contents; automatic detection of scope edits is not promised.
- Manual, one-shot, interval, and later conditional triggers share one admission
  and execution path. One-shot scheduling supports a selected date/time with
  clear timezone display. Missed starts and repeated triggers cannot cause replay
  or unbounded queues. Plan recurrence must not become implicit failure retry.
- If authorized, chaining uses validated outcomes, exact upstream provenance,
  explicit field mapping and preauthorized successors. Reject cycles, malformed
  required outputs, and duplicate dispatch in normal operation. False conditions
  mean not triggered, not execution failure; run-only bypasses successors.
- Required unit and isolated real-Pi integration checks pass. Accepted workflows
  are verified in live Emacs; incomplete manual checks remain actionable tasks.

* Approach and decisions
** Minimal concepts and sources of truth
- Only two new primary user concepts: job (reusable instruction/settings/optional
  trigger) and run (one attempt). Schedules/triggers are settings, not separate
  dashboards. A plan adapter is internal, not a second plan/workflow system.
- Reuse pichat/GLOSSARY.md terminology for runtime, Pi session, saved session
  file, settlement, presets, targets, and source/process generations.
- plan.org owns task/phase progress, gates and verification evidence. The job
  record owns dispatch, timing, execution outcome and provenance. Pi owns the
  conversation. Run history links to the plan rather than duplicating checklists.
- Existing plans skill continues to perform plan bookkeeping. The job manager
  must not mark tasks DONE because an agent stopped or JSON says complete.
- Do not introduce workflow definitions/runs, workers, or a graph language now.
  Reassess an external engine if joins or crash-resumable workflows become needed.

** Shared execution and persistence
- PiChat owns jobs, runs, admission and native timer dispatch. Reuse backend/RPC,
  launch-profile normalization, preset/tools/model/target resolution, diagnostics,
  canonical synchronization, and exact-runtime actions; do not scrape UI text.
- Current pichat-start-session changes pichat-current-session; the interactive
  launch path displays/synchronizes chats. Settlement synchronization and pending
  extension UI are chat-owned. Add a narrow noninteractive boundary rather than
  calling interactive launch commands and assuming they remain invisible.
- Initially an undisplayed owning chat may reuse existing sync/UI infrastructure;
  no large headless rewrite is required. Expose explicit readiness and synchronized
  completion contracts. Jobs must not depend on window visibility; define safe
  behavior for killing an owning buffer. Closing a window does not cancel work.
- Reuse approval interactions in the owning chat. Jobs shows Needs input and
  opens that exact chat; no second approval form or automatic approval. Resolve
  paused/waiting runtime retention, timeouts, cleanup, and explicit continuation.
- Persist versioned data-only records with atomic writes. Create a run record
  before external execution. Capture stable job/run IDs, instruction/input and
  configuration snapshots, trigger identity/kind, upstream run and optional chain
  provenance, result and saved-session references, and dispatch disposition.
- Keep execution lifecycle separate from domain outcome and attention reasons;
  finalize a small state vocabulary during UI/contracts work. Distinguish agent
  finished, synchronized result, phase complete, and human review still required.
- Retain interrupted/uncertain state after crashes; no automatic replay across
  the dispatch/acknowledgment gap. Snapshot applicable config/trigger rules so
  editing a definition during a run cannot silently change that run's behavior.
- Plan-backed runs normally retain saved sessions for auditability. Runtime
  cleanup, run-record retention, and saved-session retention are separate policies.
- Generation-scoped callbacks reject stale processes/sources and duplicate events.
  Preserve captured target/path ownership. Uncertain remote shutdown must remain
  explicit and must not release conflicting work as if the process were stopped.
- Reuse pichat-process-lifetime.el and the existing actual-Pi identity/observer
  mechanism for remote Pi exit confirmation; do not build a second SSH shutdown
  checker. Linux/procfs/helper capability limits and unknown outcomes still apply.
- Existing focused verification covers idle-runtime reconfiguration, not the full
  cancellation of active job tools/descendants. Investigate that narrower gap:
  confirmed Pi exit is not automatically evidence that every modifying descendant
  stopped or that its workspace is safe to release. Reuse available lifecycle
  evidence, define the job-specific release criterion, and retain uncertainty
  until it is resolved rather than retrying or admitting conflicting modifiers.

** Concurrency and resource ownership
- One active occurrence per definition; small configurable global run limit.
  Accepted interval policy: skip busy ticks with a visible reason, without
  accumulating a backlog or coalesced catch-up attempt. Manual queues remain
  bounded. Do not infer resource safety from job identity.
- Serialize managed conflicting modifications to the same execution workspace.
  Different projects and isolated worktrees can run in parallel unless another
  mutable resource is shared, including the authoritative plan file.
- Explicit read-only jobs may run together in one project. Read-only work that
  needs a stable snapshot waits behind modifiers; work explicitly tolerant of
  changing files may run concurrently. Resolve this choice in UI/setup, not via
  guessed prompt text. Unknown access defaults conservatively.
- This is coordination, not enforcement: read-only labels do not sandbox tools;
  Emacs-local claims do not detect all external agents or manual file edits.
  Document limits and avoid requiring a clean worktree as a substitute for safety.
- Use a minimal internal resource-claim seam, not a generic user-facing lock DSL.
  Resolve canonical target/workspace identity, same-plan conflicts, and claim
  lifetime before enabling concurrent modifying runs.

** Optional plan adapter and authorization
- Start with one exact selected phase per job. Do not autonomously select the
  next incomplete phase or infer dependencies from numbering.
- Store project/plan path and the selected full heading path; no stable Org ID
  requirement or setup-time ID insertion. Resolve only a unique matching phase;
  missing/ambiguous paths require reselection, not fuzzy or number-only retargeting.
  Rename/move tracking and detecting replacement content at the same path are
  outside scope. Run records capture the scope read at dispatch for inspection,
  not as a setup-versus-execution modification guard.
- Current plans.py exposes human-readable inventory/checks, not machine-readable
  phase eligibility. Its check validates structure, not tests or approvals. Add a
  narrow machine-readable inspection contract in the plans skill when implementing
  the adapter; do not scrape list output or duplicate lifecycle semantics in PiChat.
  Changes to this shared skill must remain backward compatible and be explicitly
  recorded/tested as cross-project scope. Prose gates are not machine proof.
- Explicitly authorize the selected phase and resolved execution policy, not later
  phases. Recheck current eligibility immediately before dispatch, using current
  saved plan contents. Do not hash/diff the plan, classify scope edits, or require
  reauthorization because the plan changed. Explain this limitation in scheduling
  review: users must disable/review scheduled work when changing its intended scope.
  Explicit edits to job execution settings remain a separate review operation.
- Existing user approval remains authoritative. Neither agent prose nor an agent-
  editable result flag proves human acceptance. Define a trusted user-action path
  and persist its evidence in the plan; unresolved approval gates stop automation.
- A phase can finish agent work while still needing review. Do not hold a runtime
  indefinitely just to represent a plan gate. Explicit continuation inspects the
  current plan and obtains appropriate authorization; it is not automatic retry.
- Completed phases do not rerun on recurring ticks. Failed/interrupted/ambiguous
  attempts require explicit intervention instead of turning recurrence into retry.
- Dispatch authorization is not a security sandbox for agent tools. Presets,
  scope instructions, and documented filesystem/external-process limits still apply.

** Scheduling and conditional chaining
- Triggers: manual first; once at a selected time; fixed interval; later after an
  eligible run. Timers enqueue only; all triggers pass the same admission checks.
- Define interval timing, overlap, restart restoration, timeouts, and disabling
  versus cancelling. Missed one-shot default: show missed and offer Run now, not
  automatic startup execution. No implicit backlog replay while Emacs was closed.
- Later chaining requires separate authorization. Define explicit successors and
  stop boundaries; show downstream effects before starting and offer Run this job
  only. Never let a diagnostic rerun unexpectedly launch a permanent chain.
- Capture trigger-rule snapshots, upstream occurrence and chain provenance. Gate
  on declared validated outcomes, not guessed prose. Pass selected fields as
  captured inputs, not shared mutable conversation state. Reject cycles; dedupe
  trigger/upstream-run dispatch in normal operation; surface crash ambiguity.
- For plans, explicit multi-phase authorization can permit separate phase runs
  (e.g. Phase 2 then Phase 3, stop before Phase 4); it does not change the plans
  skill's default one-scope stopping rule. Do not infer a successor from adjacency.
