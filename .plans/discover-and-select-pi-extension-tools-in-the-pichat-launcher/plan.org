* Goal
Let users discover extension tools and enable or disable them through simple checkboxes in PiChat's existing x Tools picker. A checked tool must be included in the runtime's startup policy and verified active before the configured launch succeeds, without extension-specific activation adapters. Registration, permission and activation remain implementation details rather than the normal picker mental model.

* Scope
- Included: target-qualified catalogue discovery, extension selections and preset baselines, startup argument generation, captured runtime/reconfiguration integration, startup activation and verification, diagnostics, tests and user documentation.
- Excluded: pi-web-access-specific support, loader/child dependency resolution or activation groups, extension-specific adapters, installing/updating packages, changing user web-search settings, enabling all extension tools implicitly, replacing MCP discovery wholesale, arbitrary live-runtime tool editing, implementing an upstream Pi RPC API, commits or implementation during planning.

* Acceptance criteria
- The existing x Tools picker gains an Extension tools section with enabled/disabled checkboxes, tool names and useful descriptions. Discovery includes registered inactive tools, but the normal picker does not display inactive labels or require users to understand exposure. Hidden tools are unselectable; technical exposure/activation information belongs in optional details or diagnostics.
- Apply, Cancel, Reset to preset and discovery refresh cover extension tools. Discovery progress/errors are clear without adding another top-level launcher option.
- Discovery runs against the intended executable/target, cwd, environment, resource/trust configuration and relevant model, without the preset allowlist hiding candidates. It is explicit, bounded, cancellable and not repeated on each redraw.
- Checked extension names reach the startup allowlist and PiChat ensures they are active before accepting a configured launch or replacement as successful, without a model request. Missing tools, rejected activation or unsupported activation semantics produce a clear failure, never silent checked-but-unavailable success. Unchecked tools are omitted under Pi's explicit selection policy. Existing explicit presets retain an empty extension baseline; standard stays pass-through.
- Selection snapshots survive restart, retry and restore. Effective-change comparisons include extension choices, and missing/stale selections are diagnosed rather than silently broadened.
- Enabling is an initial launch/replacement guarantee, not continuous enforcement: PiChat does not fight later extension-managed changes or repeatedly reactivate tools. State this boundary clearly in documentation; extension-specific loader dependencies remain outside scope and are not automatically resolved.
- Catalogue protocol data is bounded and versioned, does not become conversation content, and cannot silently fall through into a model prompt when the helper command is unavailable.
- Focused tests and pichat/test/run-tests.sh --full pass with isolated state and deterministic fake providers. Live Emacs launcher checks are recorded; README.md and GLOSSARY.md match implemented behavior.

* Approach and decisions
- Original implementation baseline: pichat-tool-picker.el offered built-ins/MCP only; pichat-mcp-discovery.el runs pi mcp list --json; pichat-tool-selection.el accepts :builtins/:mcp; pichat-presets.el restricts explicit tool names to built-ins. pichat-reconfigure.el captures selections and compares generated arguments.
- Helper location: pichat/bridge/pichat-tool-control.ts, shipped with PiChat and separate from pichat/bridge/pichat-bridge.ts (the optional Emacs-defined-tool bridge). It owns catalogue discovery and startup enable/verification. PiChat explicitly loads it with --extension for discovery probes and runtimes requiring extension-tool configuration; no installation into ~/.pi/agent/extensions/ or separate npm package is required. Resolve local paths through PiChat's package location, not hard-coded repository paths. SSH uses the private target staging strategy recorded below; never pass a host-only local path to remote Pi. Production runtime loading was implemented in Phase 2.
- Implemented Phase 1 contract: pichat-tool-control-v1 accepts JSON {protocolVersion:1, requestId, operation:"catalogue"|"enable", names?}. A reserved __pichat_tool_control_v1__ input dialog carries the correlated result; the client acknowledges it, then requires prompt disposition handled. get_state is the startup barrier; get_commands must confirm the command's extension source path before any internal command is sent. This command neither appends conversation entries nor invokes a model.
- Payload policy: at most 4096 tool records, names up to 256 characters, descriptions capped at 4096 characters, 1 MiB payload/stderr and 2 MiB total stdout. Normalize exact names, descriptions, exposure and observed active membership; hidden or CLI-pattern-unsafe names are not eligible. No provider/package provenance is inferred. The generic result is all registered tools visible under Pi policy; Phase 2 partitions exact known built-ins/MCP choices without prefix-based provenance guesses.
- Activation contract verified on Pi 1.4.0: a control command after get_state runs after awaited session_start handlers even when the control extension loads first. A one-shot setActiveTools union enables registered inactive direct, model-only, codemode and deferred tools; hidden/missing names fail before mutation. Activation cannot restore CLI-excluded tools. No background reactivation is installed.
- Target policy: local helper uses its package-relative path; SSH stages a private 0700 directory/0600 helper file under target /tmp through TRAMP, using the native target path. For discovery probes, EOF and a one-second shutdown grace precede cleanup; forced SSH teardown reports uncertain remote process cleanup, never verified success. The 25-second probe deadline excludes synchronous TRAMP file/connection setup, which retains TRAMP's own blocking/timeouts. Live SSH verification is not configured in this environment.
- Capture resource/model/trust argv and effective environment in an owner-held draft cache; redraw never probes. Context changes or explicit refresh invalidate stale callbacks using a per-request token. Discovery does not strip generic user security/tool filters to broaden policy: unsupported generic tool/session flags, positional prompts, unknown custom CLI flags and complete wrappers fail explicitly; configure custom extension options in settings instead. No preset allowlist is added to probes.
- Recommended boundary: this dedicated minimal tool-control extension exposes a versioned command over a validated internal extension-UI envelope. Prefer supported APIs getAllTools/getActiveTools; do not parse package source or infer provenance from name prefixes.
- Use a temporary no-session RPC probe for pre-launch discovery; request the catalogue after startup readiness and close stdin for orderly shutdown. Load extensions under the intended trust policy, without the preset's restrictive --tools. Discovery executes trusted extension startup code: no-session is not a side-effect sandbox. Phase 1's handling of startup dialogs, extension errors, no-model environments, wrappers and SSH helper deployment is recorded above and exercised by the focused tests (except real SSH).
- Preserve existing MCP discovery initially. Document that its shell listing cannot see extension-registered MCP servers; avoid claiming the combined catalogue is universally complete.
- Implemented :extensions alongside :builtins/:mcp and a separate :extensions preset baseline; exact checked names join startup arguments. Presets inheriting Pi tools cannot declare an extension baseline. Existing explicit presets default to none; standard remains unchanged. The user-facing contract is enabled/disabled, not merely allowed. Internally retain registration/exposure/activation metadata to validate eligibility and startup results; hide these distinctions from normal checkbox labels.
- Phase 2 production boundary: pichat-tool-runtime.el stages/loads the bundled helper only for nonempty extension selections and gates ordinary RPC readiness/input until its internal get_state/get_commands/enable exchange verifies the actual process. Internal responses do not update public source state or become prompt-acceptance events; reserved payloads do not reach the conversation UI. Failure stops the process and retains bounded diagnostics. Replacement startup receives its requested Tools snapshot, not the old committed one. Initial saved-source reload verifies again after reload handlers, before launch/replacement commit; ordinary later source switches and activation changes do not automatically reapply selections.
- Local helper cleanup follows owned process exit; forced SSH transport termination retains target staging and reports uncertain remote shutdown rather than deleting a helper an unconfirmed child might still need. Remote reconfiguration remains blocked by existing guards. Only noninteractive bridge handshake/definition sentinels are answered during discovery/control; user dialogs and bridge tool execution are never automatically answered/executed.
- Picker integration: Extension tools is a checkbox group inside x Tools, with e-prefixed shortcuts, descriptions, unavailable entries, discovery status and explicit refresh. Apply/Cancel/Reset cover all choices. The launcher/reconfiguration draft owns the cache; model/resource/environment/prompt changes invalidate it, while redraws/reopening in the same context reuse successful results. Built-ins and exact known MCP names are partitioned without provenance guesses; original MCP partial-success eligibility policy remains intact. Runtime details include selected extension names.
- The dedicated helper provides a bounded, versioned startup enable/verify operation for the actual launched process. After startup handlers, ensure selected extension tools are active through supported Pi APIs and verify the resulting set before launch/replacement commit. Do not merely copy the probe's active set or rely on --tools alone. The helper operation and supported exposure ordering were tested in Phase 1; Phase 2 wires them into configured launch/replacement and fails clearly rather than claiming activation that Pi cannot provide.
- Do not continuously enforce activation or override every before_agent_start hook. Later extension-managed activation changes are outside the initial enable guarantee. No automatic loader execution, dependency expansion, eager package conversion or package-specific adapter is included.
- Treat catalogue results as snapshots: tools can register after startup. Cache within the launch draft, invalidate on relevant context changes, and validate selected names against the actual launched runtime before accepting a successful configured launch. Do not re-use a catalogue from an unrelated live runtime.
- User decision: skip pi-web-access-specific integration because of its tooling/activation approach. No adapter, dependency grouping, package-specific diagnosis or compatibility test matrix is required. Its tools may appear through ordinary generic discovery; this is not a promise that arbitrary selections satisfy its loader dependencies. Do not blacklist or uninstall the package as part of this scope. Generic discovery/selection remains extension-agnostic.
- Source baseline: installed Pi 1.4.0 docs at /nix/store/qk1fay010yp0c2kxnn7pp23z4cjj7yhw-pi-coding-agent-1.4.0/lib/pi/docs/: cli.md (Tools), extensions.md (Tool exposure, dynamic activation, lifecycle), rpc-commands.md (prompt/get_commands; no general tool catalogue command), rpc-extension-ui.md (transport), mcp.md (shell commands do not load extensions), sdk.md (SDK/CLI resource differences).
- Additional references: installed Pi examples/extensions/dynamic-tools.ts; pichat/bridge/pichat-bridge.ts; /home/mojo/.pi/agent/npm/node_modules/pi-web-access/tool-activation.ts:63-151, index.ts:2290-2298 and README.md:1190-1222 (installed package 0.45.0). Recheck versions on execution.
- Terminology follows pichat/GLOSSARY.md: runtime configuration is not a saved Pi session property; tool declaration is distinct from extension loading.
