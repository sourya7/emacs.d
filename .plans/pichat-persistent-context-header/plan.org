* Goal
Keep context usage visible while reading or composing in PiChat, including
when the transcript is scrolled and the chat is displayed in a narrow split.

* Scope
- Included: a persistent chat header containing the runtime working directory
  and context usage; width-aware prioritization; removal of duplicate visible
  context/title information; focused tests and user documentation.
- Excluded: changing context accounting or RPC refresh boundaries, redesigning
  Jobs, changing runtime/Pi session identity, adding new controls, or unrelated
  mode-line cleanup. No implementation or commits during planning.

* Acceptance criteria
- The header remains visible while scrolling, with the working directory on
  the left and context usage on the right when space permits.
- Path text yields to context: abbreviate/truncate the path, then omit it and
  the PiChat label before clipping context at exceptionally small widths.
  Correct layout is computed per displayed window, including two windows of
  different widths showing the same chat.
- Show token usage as the primary value; add percentage only when space permits.
  Unknown occupancy never appears as zero. Preserve unknown values after
  compaction and the existing >70% warning / >90% error thresholds.
- Missing usage is visibly labelled unavailable/unknown. Accumulated request
  usage remains distinctly labelled and is never called context occupancy.
- Working-directory and usage changes update without transcript edits for
  ordinary header-only refreshes. Source rebinding cannot leave old usage visible.
- No duplicate visible scrolling title or mode-line context segment; remaining
  model/thinking controls, runtime state and queue/UI indicators still work.
- Transcript region markers, prompt editing/undo, scrolling, and export retain
  their existing semantics after the scrolling title is retired.
- Focused regression tests and pichat/test/run-tests.sh pass; live narrow/wide
  Emacs inspection verifies the layout. Outstanding visual checks remain TODO.

* Approach and decisions
- Proposed choice: option 2 from the review, a native Emacs header-line-format,
  rather than simply moving context ahead of mode-line-buffer-identification.
  This draft proposes that choice; implementation requires explicit approval.
- pichat/pichat-chat.el currently sets mode-line-format near line 562;
  pichat-chat--mode-line-status places context after variable-width metadata.
  pichat-chat--header-title / --insert-header / --refresh-header own a scrolling
  first-line title, not a fixed header. Audit their consumers before retirement;
  do not casually remove the shell on which transcript markers may depend.
- Reuse/refactor pichat-chat--format-context-usage as a shared presentation
  boundary without changing its accounting meaning. Its accumulatedRequests
  branch already explicitly distinguishes request totals from occupancy.
- Use cached runtime state only during redisplay; no RPC/file operations in
  header evaluation. Ensure redisplay and width calculations target each window.
- Jobs uses fixed header-line facilities (table headings and cached-inspection
  navigation); borrow the native mechanism, not its job-specific contents.
- Follow pichat/GLOSSARY.md: the path is the runtime working directory; the
  chat follows the runtime's active source. Keep README terminology consistent.
- Proposed wide layout:
  : PiChat — ~/.emacs.d/                    Context 84k/272k · 31%
- Proposed narrow layout:
  : PiChat — …/emacs.d/       Context 84k/272k
- Proposed very narrow layout:
  : Context 84k/272k
