* Goal
Add repeatable, named PiChat jobs with inspectable execution state and run
history, initially usable manually and optionally runnable periodically.
Design the user interface first, with an explicit user-acceptance gate.

* Scope
- Included: UI design and example; reusable job definitions; asynchronous manual
  execution; inspectable runs/results; durable definitions and run metadata;
  optional Emacs-lifetime scheduling; tests and user documentation.
- Excluded: execution while Emacs is closed, distributed workers, automatic
  retries, implicit approvals, and general-purpose arbitrary Lisp job execution.
- Implementation details below are provisional until the UI phase resolves the
  workflows. Creating this draft does not authorize implementation.

* Acceptance criteria
- Phase 1 produces a concrete UI example covering job listing, definition
  editing, run inspection/history, manual execution, and schedule controls.
- The user explicitly accepts that example. Record the accepted artifact and
  approval evidence here; silence or approval of this plan is not UI acceptance.
- No feature implementation starts before that gate passes.
- A named definition can be run repeatedly without mutating the preferred
  interactive runtime; individual runs retain their own identity and state.
- Users can inspect active/completed/failed/cancelled runs and required input,
  access results and the owning conversation, and cancel active work.
- Definitions and settled run metadata survive Emacs restart; interrupted runs
  are represented honestly rather than reported as successful or blindly retried.
- Optional scheduling invokes the same execution path as manual runs, with
  explicit overlap, missed-run, and enable/disable behavior.
- Required unit and isolated real-Pi integration checks pass; the approved UI
  workflows are verified in live Emacs before whole-plan completion.

* Approach and decisions
- Consult pichat/GLOSSARY.md for runtime, Pi session, saved session file, and
  settlement terminology; update it only if new shared concepts need definition.
- Existing reference points: pichat-session-manager.el uses tabulated-list-mode,
  cached row refresh, pending-input indicators, and exact-runtime actions.
  pichat-backend.el provides lifecycle, prompt, abort, state, and transcript APIs.
- Prefer a focused job layer over moving PiChat objects to another Emacs process.
  Keep definitions, run records, scheduling, and runtime execution distinct.
- Candidate UI: a separate jobs view plus run inspection/history; do not overload
  runtime-manager rows with job-definition identity. Layout and keys are not yet agreed.
- Candidate defaults: fresh independent runtime/Pi session per occurrence; no
  focus stealing or automatic retry; bounded concurrency and one active run per
  definition. Resolve skip versus coalesce during design rather than assume it.
- Capture definition/configuration snapshots per run; distinguish submission
  acceptance, agent settlement, synchronized results, and domain-level outcome.
- Use native timers only to enqueue work. Generation-scoped callbacks must not
  affect rebound sources or replacement processes. Respect target/transport and
  startup preset boundaries; define runtime cleanup and retention explicitly.
- Resolve storage/schema, schedule vocabulary, timezone behavior, unattended
  interaction, retention, and recovery policy before implementing their phase.
- Related but distinct plan: [[file:../pichat-delayed-follow-up/plan.org][PiChat delayed follow-up]].
  Reusable job scheduling must not duplicate its conversation-message checklist.
