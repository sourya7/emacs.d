* Goal
Let users discover extension tools and enable or disable them through simple checkboxes in PiChat's existing x Tools picker. A checked tool must be included in the runtime's startup policy and verified active before the configured launch succeeds, without extension-specific activation adapters. Registration, permission and activation remain implementation details rather than the normal picker mental model.

* Scope
- Included: target-qualified catalogue discovery, extension selections and preset baselines, startup argument generation, captured runtime/reconfiguration integration, startup activation and verification, diagnostics, tests and user documentation.
- Excluded: pi-web-access-specific support, loader/child dependency resolution or activation groups, extension-specific adapters, installing/updating packages, changing user web-search settings, enabling all extension tools implicitly, replacing MCP discovery wholesale, arbitrary live-runtime tool editing, implementing an upstream Pi RPC API, commits or implementation during planning.

* Acceptance criteria
- The existing x Tools picker gains an Extension tools section with enabled/disabled checkboxes, tool names and useful descriptions. Discovery includes registered inactive tools, but the normal picker does not display inactive labels or require users to understand exposure. Hidden tools are unselectable; technical exposure/activation information belongs in optional details or diagnostics.
- Apply, Cancel, Reset to preset and discovery refresh cover extension tools. Discovery progress/errors are clear without adding another top-level launcher option.
- Discovery runs against the intended executable/target, cwd, environment, resource/trust configuration and relevant model, without the preset allowlist hiding candidates. It is explicit, bounded, cancellable and not repeated on each redraw.
- Checked extension names reach the startup allowlist and PiChat ensures they are active before accepting a configured launch or replacement as successful, without a model request. Missing tools, rejected activation or unsupported activation semantics produce a clear failure, never silent checked-but-unavailable success. Unchecked tools are omitted under Pi's explicit selection policy. Existing explicit presets retain an empty extension baseline; standard stays pass-through.
- Selection snapshots survive restart, retry and restore. Effective-change comparisons include extension choices, and missing/stale selections are diagnosed rather than silently broadened.
- Enabling is an initial launch/replacement guarantee, not continuous enforcement: PiChat does not fight later extension-managed changes or repeatedly reactivate tools. State this boundary clearly in documentation; extension-specific loader dependencies remain outside scope and are not automatically resolved.
- Catalogue protocol data is bounded and versioned, does not become conversation content, and cannot silently fall through into a model prompt when the helper command is unavailable.
- Focused tests and pichat/test/run-tests.sh --full pass with isolated state and deterministic fake providers. Live Emacs launcher checks are recorded; README.md and GLOSSARY.md match implemented behavior.

* Approach and decisions
- Current implementation: pichat-tool-picker.el offers built-ins/MCP only; pichat-mcp-discovery.el runs pi mcp list --json; pichat-tool-selection.el accepts :builtins/:mcp; pichat-presets.el restricts explicit tool names to built-ins. pichat-reconfigure.el captures selections and compares generated arguments.
- Helper location: pichat/bridge/pichat-tool-control.ts, shipped with PiChat and separate from pichat/bridge/pichat-bridge.ts (the optional Emacs-defined-tool bridge). It owns catalogue discovery and startup enable/verification. PiChat explicitly loads it with --extension for discovery probes and runtimes requiring extension-tool configuration; no installation into ~/.pi/agent/extensions/ or separate npm package is required. Resolve local paths through PiChat's package location, not hard-coded repository paths. SSH targets need a runtime-accessible helper deployment/path strategy, to be settled in Phase 1; never pass a host-only local path to remote Pi.
- Recommended boundary: this dedicated minimal tool-control extension exposes a versioned command over a validated internal extension-UI envelope. Prefer supported APIs getAllTools/getActiveTools; do not parse package source or infer provenance from name prefixes.
- Use a temporary no-session RPC probe for pre-launch discovery; request the catalogue after startup readiness and close stdin for orderly shutdown. Load extensions under the intended trust policy, without the preset's restrictive --tools. Discovery executes trusted extension startup code: no-session is not a side-effect sandbox. Define handling for startup dialogs, extension errors, no-model environments, wrappers and SSH helper deployment before implementing the probe.
- Preserve existing MCP discovery initially. Document that its shell listing cannot see extension-registered MCP servers; avoid claiming the combined catalogue is universally complete.
- Add :extensions alongside :builtins/:mcp and a separate explicit preset extension baseline; union exact checked names into startup arguments. The user-facing contract is enabled/disabled, not merely allowed. Internally retain registration/exposure/activation metadata to validate eligibility and startup results; hide these distinctions from normal checkbox labels.
- Extend the dedicated helper with a bounded, versioned startup enable/verify operation for the actual launched process. After startup handlers, ensure selected extension tools are active through supported Pi APIs and verify the resulting set before launch/replacement commit. Do not merely copy the probe's active set or rely on --tools alone. Establish exact ordering and unsupported-exposure behavior with real-Pi fixtures in Phase 1; fail clearly rather than claim activation that Pi cannot provide.
- Do not continuously enforce activation or override every before_agent_start hook. Later extension-managed activation changes are outside the initial enable guarantee. No automatic loader execution, dependency expansion, eager package conversion or package-specific adapter is included.
- Treat catalogue results as snapshots: tools can register after startup. Cache within the launch draft, invalidate on relevant context changes, and validate selected names against the actual launched runtime before accepting a successful configured launch. Do not re-use a catalogue from an unrelated live runtime.
- User decision: skip pi-web-access-specific integration because of its tooling/activation approach. No adapter, dependency grouping, package-specific diagnosis or compatibility test matrix is required. Its tools may appear through ordinary generic discovery; this is not a promise that arbitrary selections satisfy its loader dependencies. Do not blacklist or uninstall the package as part of this scope. Generic discovery/selection remains extension-agnostic.
- Source baseline: installed Pi 1.4.0 docs at /nix/store/qk1fay010yp0c2kxnn7pp23z4cjj7yhw-pi-coding-agent-1.4.0/lib/pi/docs/: cli.md (Tools), extensions.md (Tool exposure, dynamic activation, lifecycle), rpc-commands.md (prompt/get_commands; no general tool catalogue command), rpc-extension-ui.md (transport), mcp.md (shell commands do not load extensions), sdk.md (SDK/CLI resource differences).
- Additional references: installed Pi examples/extensions/dynamic-tools.ts; pichat/bridge/pichat-bridge.ts; /home/mojo/.pi/agent/npm/node_modules/pi-web-access/tool-activation.ts:63-151, index.ts:2290-2298 and README.md:1190-1222 (installed package 0.45.0). Recheck versions on execution.
- Terminology follows pichat/GLOSSARY.md: runtime configuration is not a saved Pi session property; tool declaration is distinct from extension loading.
