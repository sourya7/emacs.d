* Goal
Deliver a follow-up submitted during manual compaction automatically after successful compaction, without requiring an unrelated prompt to wake the agent.

* Scope
- Included: PiChat manual-compaction/follow-up coordination, safe dispatch and recovery, regression coverage, user-facing documentation.
- Excluded: delayed scheduling, changing automatic-compaction semantics, unrelated queue redesign, upstream Pi modifications, commits and compatibility-watermark changes.
- Related but separate: [[file:../pichat-delayed-follow-up/plan.org][delayed follow-up scheduling]] adds timers and compact-then-continue jobs; this plan fixes immediate follow-ups only and does not duplicate that work.

* Acceptance criteria
- A follow-up submitted while PiChat-requested manual compaction is running starts automatically after correlated successful completion, without an unrelated prompt or synthetic conversation message.
- Multiple follow-ups preserve order and configured delivery mode; no message is lost or delivered twice. Existing queued messages must not be cleared and reconstructed from text alone if that would lose images or other semantics.
- Failed, aborted or ambiguously completed compaction never silently dispatches the waiting follow-up; retained text is recoverable and the UI explains its disposition.
- A source rebind, runtime stop/restart, stale callback, repeated completion notification or overlapping ordinary submission cannot dispatch into the wrong Pi session or duplicate work.
- Ordinary in-run follow-ups and automatic-compaction continuation remain unchanged. Unsent draft and attachments remain intact.
- Focused ERT and isolated real-Pi fake-provider integration tests pass; unit and full suite results are recorded.

* Approach and decisions
- User confirmed the observed compaction was manual. Static inspection of installed Pi 1.4.0 shows manual =compact()= emits =compaction_end= and returns without consuming queued messages; automatic compaction checks =agent.hasQueuedMessages()= to continue.
- =pichat/pichat-chat.el=: =pichat-chat-follow-up= forwards immediately through =pichat-rpc-follow-up=; =pichat-chat-compact= sends =compact=; the compaction-end handler only refreshes stats/transcript. =pichat/pichat-rpc.el= implements the RPC wrappers.
- Resolve the dispatch mechanism before implementation: verify whether supported RPC can resume an existing queue without a fabricated prompt. If not, prefer narrowly scoped Emacs-owned pending submissions during manual compaction, released through the normal submission path after correlated success, rather than enqueueing work that cannot wake itself. Record how earlier native queued messages and delivery modes are preserved; ask the user if a required tradeoff changes the acceptance contract.
- Correlate the initiating compaction response with runtime/source/process identity; do not treat any compaction-end event as blanket permission to send. Revalidate current activity before dispatch and define races with an ordinary prompt explicitly.
- Use terminology from =pichat/GLOSSARY.md=. Inspect current submission/recovery, lifecycle guards and backend capabilities before adding state; avoid unconditional backend-specific behavior in generic code.
- Existing integration coverage includes manual compaction success/failure and steering/follow-up queue round-trips in =pichat/test/pichat-test-integration.el=. Extend focused behavioral coverage using existing isolated fake-provider support.
